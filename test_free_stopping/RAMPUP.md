## 1. The project in two paragraphs

**Question.** Can we tell when to stop training *without looking at test data*, in a way
that is not fooled by grokking? Under grokking, training accuracy hits 100% early, then
test accuracy sits flat for a long time before jumping. Standard early stopping (patience
on validation loss), and the published validation-free stopping rules we found
(Mahsereci et al. 2017, gradient disparity, Label Wave), are expected to stop on that
plateau. We want a **causal** signal: the decision at step t uses only data up to t,
built from training data, weights, gradients and hyperparameters. Test accuracy is used
only to score the rule. The main score is **regret**: best test accuracy over the run
minus test accuracy at the stopping step.

**Approach.**
- One architecture (a plain MLP, no normalization) and three applications: modular
  arithmetic, an MNIST subset, and teacher–student regression.
- Four optimizers: AdamW, Adam+L2, SGD+momentum, SGD.
- A sweep over weight decay γ, init scale α and training-set size, with 4 seeds.
- The resulting corpus has **1,664 runs**: grokkers, fast learners, never-generalizers,
  joint plateaus and late collapses.
- Each run stores dense cheap telemetry plus sparse **keyframes**. Anything else at any
  step is regenerated by **bit-exact deterministic replay**.
- Candidate signals and published baselines are then computed offline, with causality
  enforced in code, and turned into stopping rules. Rules are calibrated on seeds {0, 1}
  and scored on held-out seeds {2, 3}.

**History.** This repo (`BTP/`) is a student research project. It started in
`agop_alignment_testing/` (reproducing Mallinar et al.'s RFM/AGOP grokking paper), then
pivoted to the stopping question in a fresh codebase, `test_free_stopping/`. The two
share no code or results.

## 3. Working rules with the user (non-negotiable)

1. **Scope.** Only touch `test_free_stopping/` (and, if asked, `agop_alignment_testing/`).
   Never touch `Grokking_implementation_assimilate/`, the root PDFs or other root files.
2. **Git.** Never commit or push. When work is ready, stop and tell the user what changed;
   they commit and push. Molab pulls code from GitHub
   (`github.com/Rishith01/Characterising-Grokking`), so nothing runs on Molab until the
   user has pushed.
3. **Molab runs.** Anything that needs the GPU or Hugging Face is a **marimo notebook**
   (a `.py` file, not `.ipynb`) in `molab/`. You write it; the user runs it. Every
   notebook has a "Clone / pull" cell, an environment check against
   `configs/env_lock.txt`, and asks for the HF token in a **password field**. Never store
   or log the token.
4. **Hugging Face.** Account `advay333`, public dataset repos. Do uploads and downloads
   from Molab. Reading public repos locally to analyse results is fine and normal: use
   `huggingface_hub.snapshot_download` with `allow_patterns` into the scratchpad. Pass
   Windows-style paths (`C:/...`), not Git-Bash `/c/...`, or Python creates a stray
   `C:\c\` tree.
5. **One phase step at a time.** Don't start the next phase, or the next dataset in
   Phase 3, until the user asks. When a run finishes, analyse it, say whether it is as
   expected, record it in `results/`, and list decisions. Recommend one option rather
   than surveying all of them.
6. **Notebook output.** Print every table to the console as it is produced, and upload a
   `summary.md` alongside the JSON reports. Molab's UI can fail to render after long cells.
7. **Decisions belong to the user**, e.g. grid levels, what to drop, deleting HF data.
   Ask; don't assume.

## 5. Invariants you must not break

These are the load-bearing design rules. Each one has a test.
1. **One step implementation.** `TrainLoop.step` is used by both training and replay.
   Never fork it.
2. **Recording is side-effect-free.** No recording code may touch `p.grad`, optimizer
   state or the training seed streams.
3. **Determinism.** `determinism.apply()` runs before any CUDA work; entry points call
   `cpu_env.pin()` before importing torch; the launcher's `child_env` gives every worker
   the pinned variables and a thread share. Any new randomness needs its **own named
   seed stream**, appended at the end of `seeding.STREAMS`, never reordered.
4. **Test-data quarantine.** Only `tfs/evaluation/oracle.py` reads `oracle.parquet`
   (other evaluation code goes through its `Oracle` class).
   `TrainContext` carries no test tensors. `tests/test_quarantine.py` scans signal, rule,
   causal, reader and replay code. lr selection (`tfs/sweep/lr_select.py`) reads training
   telemetry only.
5. **Causality.** Signals (Phase 4) see only a forward-only stream; every signal must
   pass the perturb-the-future test (DESIGN §7.4).
6. **Immutable run files.** Everything listed in `checksums.json` is never modified after
   training. Mutable state (the replay level) lives in `replay_report.json` and the
   manifest.
7. **Small summaries.** Dense summaries hold only O(width) numbers per layer; anything
   O(width²) comes from replay.
8. **Frozen corpus configs.** `configs/sweeps/phase3_*.yaml` are the record of the grid,
   and run ids are hashes of the full config. Changing any value, or writing an int where
   a float was (`1` vs `1.0`), changes the run ids and silently creates a new run.
   `tests/test_corpus.py` checks the files against PLAN §3.

## 6. Lessons learned (so you don't repeat them)

- **GPU determinism is solid.** Every replay so far is L0 with zero error: Phase 1,
  24/24 final configs under MPS, 1,021 corpus and pilot runs, and the full-replay audits.
  Identical configs reproduce exactly across Molab sessions.
- **MPS roughly doubles throughput** (≈2,450 vs ≈1,380 steps/s at 16 workers) and stays
  bit-identical; more than 16 workers doesn't help.
- **CPU determinism needed pinning** (dynamic threading / oneDNN). The corpus is GPU-only.
- **YAML 1.1 (pyyaml) reads `3e-4` as a string.** Always write `3.0e-4`. Write floats as
  `1.0`, not `1`, or the run-id hash changes.
- **On Windows, Python's text mode writes CRLF.** When copying a notebook, use bytes or
  `newline="\n"`, or a diff shows every line changed.
- **Loss-only lr selection is fooled by the mean predictor.** MNIST depth 8 at α = 1 drops
  to the constant-output loss and never learns. `lr_select.classify` now also requires
  fitting.
- **Check accuracy definitions against the data scale.** Teacher–student uses RMS error
  < 0.01 per sample; MSE < θ was 100× too loose.
- **Coupled weight decay caps fitting.** With MSE and a tight θ, γ ≥ 1e-4 (coupled) stops
  teacher–student fitting; at depth 8 it can pull MNIST to the constant output.
- **Published setups don't always reproduce.** Deep Grokking's two-stage generalization
  didn't; x²+xy+y² never generalized and was replaced by x/y.
- **The provisional run categories** (`run_summary.provisional_category`, a 10×/2× ratio
  rule) mislabel slow creeps. Use them for counts only; regret does not depend on them.
  Phase 5's `GroundTruth` should classify from curve shape.
- **`.gitignore` patterns must be anchored** (`/runs/`, not `runs/`).

## 7. Environment and how to work locally

- **Machine:** Windows 11, Python 3.13. Git Bash (POSIX syntax) and PowerShell. Work
  from `BTP/test_free_stopping/`.
- **Local venv:** `.venv` (CPU-only torch). Run everything with `.venv/Scripts/python.exe`.
  Tests: `.venv/Scripts/python.exe -m pytest -q` (83 tests, about 3–4 min). Lint
  notebooks with `.venv/Scripts/marimo.exe check molab/<file>.py`.
- **No MNIST locally.** Tests use synthetic IDX files.
- **Molab:** NVIDIA RTX PRO 6000 Blackwell (96 GB), 20 CPUs, sessions up to 12 h, files do
  not persist. The pinned stack is in `configs/env_lock.txt` (torch 2.11.0+cu130, CUDA
  13.0, driver 595.71). Every notebook checks the live environment against it.
- **Editing tip:** for multi-line edits with escapes or quotes, write a small Python edit
  script to the scratchpad (or use the Edit tool). Never use a bare `cat > file` without
  a heredoc: it waits on stdin forever.
