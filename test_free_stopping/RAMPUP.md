# Ramp-up: taking over `test_free_stopping`

This is the starting point for a new agent (or person) picking up the project at
**Phase 2**. Read this file, then the documents in §2, and you should be able to plan and
run the Phase 2 pilot. Written 2026-10-21, at the end of Phase 1.

---

## 1. The project in two paragraphs

**Question.** Can we tell when to stop training *without looking at test data*, in a way
that is not fooled by grokking? Under grokking, training accuracy hits 100% early, then
test accuracy sits flat for a long time before jumping. Standard early stopping (patience
on validation loss) and every published validation-free stopping rule we found
(Mahsereci et al. 2017, gradient disparity, Label Wave) stop on that plateau. We want a
**causal** signal: the decision at step t uses only data up to t, built from training
data, weights, gradients and hyperparameters. Test accuracy is used only to score the
rule. The main score is **regret**: best test accuracy over the run minus test accuracy
at the stopping step.

**Approach.** One architecture (a plain MLP), three applications (modular arithmetic,
an MNIST subset, teacher–student regression), four optimizers, and a sweep over weight
decay, init scale and training-set size. The sweep produces a corpus of about 1,660 runs
containing grokkers, fast learners, never-generalizers and late collapses. Each run
stores dense cheap telemetry plus sparse **keyframes**. Anything else at any step is
regenerated by **bit-exact deterministic replay**. Candidate signals (objective
stationarity, weight norm, spectra/rank, feature stationarity) and published baselines
are then computed offline with causality enforced in code, turned into stopping rules,
calibrated on seeds {0, 1}, and scored on held-out seeds {2, 3}.

**History.** This repo (`BTP/`) is a student research project. It started in
`agop_alignment_testing/`: reproducing Mallinar et al.'s RFM/AGOP grokking paper and
trying to *forecast* grokking. The user then pivoted to the stopping question and asked
for a fresh, clean codebase. That is `test_free_stopping/`. No code or results are shared
between the two.

## 3. Working rules with the user (non-negotiable)

1. **Scope.** Only touch `test_free_stopping/` (and, if asked, `agop_alignment_testing/`).
   Never touch `Grokking_implementation_assimilate/`, the root PDFs or other root files.
2. **Git.** Never commit or push. When work is ready, stop and tell the user what changed;
   they commit and push. Molab pulls code from GitHub
   (`github.com/Rishith01/Characterising-Grokking`), so nothing runs on Molab until the
   user has pushed.
3. **Molab runs.** Anything that needs the GPU or Hugging Face is a **marimo notebook**
   (a `.py` file, not `.ipynb`) in `molab/`. You write it; the user runs it on Molab
   from a clone of the repo. Every notebook has a "Clone / pull" cell and asks for the HF
   token in a **password field**. Never store or log the token.
4. **Hugging Face.** Account `advay333`, public dataset repos. Do uploads and downloads
   from Molab. If you ever upload from local, make sure HF ends up with the latest
   version and delete the local copy. *Reading* public HF repos locally to analyse
   results is fine and has been the normal way to read Molab outputs (use
   `huggingface_hub.snapshot_download` with `allow_patterns` into the scratchpad, then
   delete).
5. **Phases.** Don't start the next phase until the user asks. When a run finishes,
   analyse it, report the result and conclusions, and list decisions for the user.
   Recommend an option rather than surveying all of them.
6. **Notebook output.** Print every result table to the console as it is produced, and
   upload a `summary.md` alongside the JSON reports (`tfs/evaluation/report.py`).
   Phase 1b's tables never rendered, and the results had to be recovered from HF.
7. **Decisions belong to the user**, e.g. grid levels, what to drop, deleting HF data.
   Ask; don't assume.

## 4. Environment and how to work locally

- **Machine:** Windows 11, Python 3.13. Tools: PowerShell and Git Bash (POSIX syntax in
  Bash). Work from `BTP/test_free_stopping/`.
- **Local venv:** `test_free_stopping/.venv` (CPU-only torch 2.13). Run everything with
  `.venv/Scripts/python.exe`. Tests: `.venv/Scripts/python.exe -m pytest -q` (64 tests,
  about 80 s). Lint notebooks with `.venv/Scripts/marimo.exe check molab/<file>.py`.
- **No MNIST locally.** Tests use synthetic IDX files. MNIST is downloaded on Molab by
  `ensure_mnist()`.
- **Molab:** NVIDIA RTX PRO 6000 Blackwell (96 GB), 20 CPUs, sessions up to 12 h, files do
  not persist. Its `/proc/cpuinfo` lacks a model name; `cpu_env.cpu_model()` now tries
  several sources.
- **Editing tip:** for multi-line edits that contain escapes (`\n`) or quotes, write a
  small Python edit script to the scratchpad and run it, or use the Edit tool. Inline
  heredocs mangled escapes twice in Phase 1 and produced broken notebooks; `marimo
  check` caught both.

## 5. Invariants you must not break

These are the load-bearing design rules. Each one has a test.
1. **One step implementation.** `TrainLoop.step` is used by both training and replay.
   Never fork it.
2. **Recording is side-effect-free.** No recording code may touch `p.grad`, optimizer
   state or the training seed streams. Test: recording cadence does not change keyframe
   hashes.
3. **Determinism.** `determinism.apply()` runs before any CUDA work; entry points call
   `cpu_env.pin()` before importing torch; the launcher's `child_env` gives every worker
   the pinned variables and a thread share. Any new randomness needs its **own named
   seed stream**, appended at the end of `seeding.STREAMS`, never reordered.
4. **Test-data quarantine.** Only `tfs/evaluation/oracle.py` reads `oracle.parquet`.
   `TrainContext` carries no test tensors. `tests/test_quarantine.py` scans signal, rule,
   causal, reader and replay code.
5. **Causality.** Signals (Phase 4) only see a forward-only stream; every signal must
   pass the perturb-the-future test (DESIGN §7.4).
6. **Immutable run files.** Everything listed in `checksums.json` is never modified after
   training. Mutable state (the replay level) lives in `replay_report.json` and the
   manifest.
7. **Small summaries.** Dense summaries hold only O(width) numbers per layer. Anything
   O(width²) comes from replay. Phase 1 broke this and ended up 10× over the storage
   budget.

## 6. Lessons learned in Phases 0–1 (so you don't repeat them)

- **GPU determinism is solid:** L0 with zero error on every config and optimizer, across
  two separate Molab runs, and at every concurrency level and under MPS.
- **CPU determinism needed pinning** (dynamic threading / oneDNN). The corpus is GPU-only
  anyway. The fix passed one 16-config check under load: evidence, not proof.
- **Throughput is CPU-bound, not GPU-bound.** More GPU workers made things *slower*
  (8 → 488, 16 → 109, 32 → 24 aggregate steps/s) because each process started one thread
  per core, and the batch order was rebuilt on the CPU every step. Both are fixed;
  re-measure in the pilot before choosing the worker count.
- **Check your accuracy definitions against the data scale.** Teacher–student's
  threshold was 100× too loose at first. Accuracy plateaued near 0.88 while the loss
  showed clear grokking.
- **Check run sizes early.** Dense WᵀW summaries made runs 10× larger than planned.
- **SGD at large init scale diverges on MNIST** at any learning rate; hence the
  SGD-family α levels {1, 2, 4} on MNIST (decision a).
- **Published setups don't always reproduce.** Deep Grokking's two-stage generalization
  didn't, at depth 8 or 12. Report it honestly and adapt.
- **The α = 1 MNIST control collapses late** (test 0.92 → 0.57 while train stays at
  100%). That is a free "late collapse" case, which punishes stopping rules that stop
  late.
- **`.gitignore` patterns must be anchored** (`/runs/`, not `runs/`): an unanchored rule
  once hid `configs/runs/` from git, and Molab couldn't find a config.
